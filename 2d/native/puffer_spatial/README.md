# Spatial cartpole for PufferLib 5

Native CPU MuJoCo environment with two continuous actions, intended for
PufferLib's CUDA policy trainer. Physics stays float64; observations are float32.
There is no Python call, allocation or rendering inside a normal native step.
The model is shared, and every instance owns independent MuJoCo data.

`spatial_core.h` implements the original RK4 stepping, radial 80 N delivery,
free ball joints, substep rail/warning checks, world tilt and 30 s / 5 s gate.
`spatial_cartpole.h` implements PufferLib 5's real Agent/puf_* interface and
auto-reset/log handling. Compile once per link count. Normalized observations
retain every quaternion and velocity, plus previous XY force and elapsed time.

Training starts hanging without waiting. Its independent SplitMix64 reset stream
samples the original perturbation ranges; its seeds are **not** NumPy reset seeds.
Evaluation injects canonical initial states generated by the original environment.
`normalized_effort=1` changes only training reward's force penalty from
`.001 * force²` to `.01 * force² / 80²`; set it to zero for the original reward.
Neither reward defines successful qualification. Learned-policy qualification
is tracked separately from these interface and throughput checks.

## Locally verified prototype

From the lab virtual environment on Windows:

```powershell
python scripts/build_puffer_native_probe.py --out output/my_native_build --links 1 2 8
python scripts/verify_puffer_native.py --build output/my_native_build --out output/my_native_checks
```

In the published repository checkout, add
`--baseline-root research/pufferlib5_native_20261017/baselines` to use the two
included previously qualified tapes instead of this lab's output directories.

The builder uses the existing MSVC compiler and MuJoCo DLL/headers. It fetches
the pinned PufferLib headers and Raylib 5.5 public header, records their hashes,
and compiles the actual environment adapter. CUDA/PufferLib training is not
needed for these checks. `verify_bridge.cpp` is only the test/benchmark bridge.

The first completed run is `output/pufferlib5_native_env_001/summary.json`:
1/2/8-link state/command parity, complete saved qualified 1/2-link episodes,
PufferLib observation/terminal/auto-reset/log checks, both force axes, clipping,
and byte-identical serial/parallel benchmark outcomes. It charged 160,344 native
integrations. The 64-instance eight-link CPU microbenchmark measured about
20,032 control transitions/s with four native threads versus 2,241/s through
the original Python loop. This is a short matched stepping measurement,
**not** end-to-end RL throughput or a solved new count.

## Isolated Linux/WSL2 integration

Use a separate checkout pinned to
`ea7f989371270d2948f96728bda8aec5e7634a4c`, then run this repository's preparation
driver using its lab Python environment (the checkout can be prepared on Windows
and consumed under WSL). It only adds new files and leaves upstream build.sh intact:

```powershell
python scripts/prepare_puffer_environment.py --checkout PATH_TO_PINNED_CHECKOUT --links 1
```

Inside Linux/WSL, with the PufferLib 5 toolchain and MuJoCo **3.3.5 Linux** SDK:

```bash
export MUJOCO_DIR=/absolute/path/to/mujoco-3.3.5
export MUJOCO_LIBRARY="$MUJOCO_DIR/lib/libmujoco.so.3.3.5"
bash build_spatial.sh spatial_cartpole spatial_n1 --float
./spatial_n1 train
```

The example config starts at 64 environments and 999,424 control transitions
(244 complete 4,096-transition batches, within the one-million budget).
The environment name is compiled into the executable, not a positional CLI argument.
Final automatic evaluation is disabled; use separately recorded evaluation plans.
It is an initial experiment, not tuned hyperparameters. Rebuild in another
isolated checkout for the next count. Version 5 `--cpu` is evaluation only;
`--float` selects float32 training on the existing Turing GPU. The CUDA trainer
build and learning runs now execute in the dedicated Cartpole-Puffer5 WSL2
distribution. The first one-link learners remain unqualified; see
`research/pufferlib5_environment.md`. Native rendering is a no-op;
qualification videos must use saved full-state tapes and the existing renderer.

## Recorded evaluation and bounded training

Prepare a separate evaluation checkout with `--evaluation-io`. This compiles in
fixed-state plan loading and create-only binary traces; ordinary training has
capture compiled out. Native traces contain pre-step observations, policy
actions, delivered forces, every post-state, tilts, terminal gates and physical
integration counters. They are written before auto-reset. Exhausting a plan
does not start extra physics. The optional `env.accounting_file` writes totals
only after all native environments have closed.

```powershell
python scripts/build_puffer_native_probe.py --out output/io_build --links 1 2 8 --evaluation-io
python scripts/verify_puffer_eval_io.py --build output/io_build --out output/io_checks
```

The recorded-interface checks cover full synthetic upright episodes, noisy
hanging motion, rail failure, nonfinite policy rejection, EOF and corrupted
trace rejection. These are diagnostic cases, not learned swing-up results.
`scripts/puffer_eval_io.py plan` creates the original 13/45-case development
cohorts and freezes a supplied checkpoint; `import` independently verifies
actual recorded transitions and exports full-state NPZ tapes. It does not prove
neural inference; a frozen GPU closed-loop rerun is still required.

For a recorded GPU evaluation use exactly one environment, including all three
vector overrides (upstream does not adjust num_buffers when eval_agents changes):

```bash
./spatial_eval eval /absolute/frozen_policy.bin --headless \
  --base.eval_episodes=13 --base.eval_agents=1 \
  --vec.total_agents=1 --vec.num_buffers=1 --vec.num_threads=1 \
  --train.horizon=64 --train.minibatch_size=64 \
  --env.evaluation_plan=/absolute/plan/plan.bin \
  --env.trace_directory=/absolute/new_trace_directory \
  --env.accounting_file=/absolute/new_trace_directory/accounting.json
```

The trace directory must already exist and be empty. Use the same MuJoCo shared
library in the native binary and Python replay, rather than assuming bitwise
identity across Windows and Linux builds. `render_puffer_evaluation.py` renders
the complete imported tape with an XY inset and explicit diagnostic/development
labels. It never labels a development tape as qualified.

The preparation driver now also adds `spatial_patches/pufferl.cu` and `algo.cu`.
The pinned upstream allocator inserts 16-byte gaps which its flat tensor lengths
and Muon tensor walk omit. With two continuous actions this truncates the final
two float32 weights and shifts recurrent optimizer slices. The copied trainer
uses physical byte spans and aligned optimizer offsets. Tracked upstream files
are unchanged. `verify_puffer_weight_layout.py` host-compiles the actual pinned
allocator/registration bodies, reproduces the original issue and verifies the
correction for 1/2/8 links, two precision sizes and discrete controls. It does
not run CUDA. The upstream CPU checkpoint reader is not supported for this path.

From the lab/2d repository, prepare a fresh training checkout, then create a plan:

```bash
python scripts/run_puffer_training.py --checkout /absolute/puffer_training \
  --out /absolute/new_smoke_plan --steps 4096
```

The default performs a dry run only. Under Linux, add `--execute` with a new
output directory to build `--float` and run the experiment. The launcher freezes
inputs and commands, checks the native/Python library identity, caps build and
training wall time, verifies actual shutdown integration counts and the complete
finite checkpoint, and disables automatic final evaluation. The first registered
seed is 73; the subsequent initial learning budget is 999,424 transitions.
The Linux GPU smoke test passes with exact integration accounting and a complete
finite checkpoint. Recorded hanging-start development pilots also pass capture,
cold replay and separate GPU first-case repeat checks, but have not solved the
task. `run_puffer_evaluation.py` automates those checks from a completed training
directory and a separate capture-enabled integration.

`setup_puffer_wsl.sh` records the dedicated Ubuntu toolkit setup; run it only
inside Cartpole-Puffer5 as root. `execute_puffer_wsl.sh` sets the tested Linux
CUDA/Python environment and invokes training, or evaluation with `--evaluate`.
It uses the existing Windows GPU driver through WSL. The explicit `extended`
training budget tier permits at most9,998,336 controls; the default `initial`
tier keeps its999,424 cap. Every run still requires a new output directory.

The paired learning experiment adds `--reward-offset 2` during preparation;
default0 preserves previous reward behavior. A positive offset addresses the
negative-return incentive to terminate early without changing physical dynamics
or the success gate. `--learning-rate 0.015` selects the pinned Puffer default;
the conservative starter remains0.001. These are registered development
comparisons, not a broad sweep or a solved-count claim.

Puffer's default GPU evaluator keeps Gaussian exploration. To deploy the policy
mean, prepare a separate evaluation integration with both `--evaluation-io` and
`--deterministic-evaluation`. This changes only copied GPU sampler source and is
rejected for training preparation. The recorded evaluator identifies `gpu_mean`
or `gpu_sampled` in plans, tapes and reports, preserves the trained checkpoint,
and repeats the first complete GPU episode independently. Both modes must meet
the original physical gates before any qualified result is claimed.
